# PM Decision Package (PM-AUTO-03)

Converts a completed task's review into three files under `automation/review/`,
generated by `automation/generate_decision_package.py`:

```
review/
  review_summary.md    human-readable summary
  review_decision.json machine-readable, fixed-schema decision
  next_task_draft.md   structured draft for the next task
```

This is a second, more structured layer on top of what PM-AUTO-01 already
produces (`review/review_request.md`, the quality-check detail package;
`tasks/NEXT_TASK_DRAFT.md`, the freeform Backlog-aware suggestion). The two
layers serve different purposes and both still run — see
`automation/README.md`'s folder structure for how they relate.

## Why a separate, fixed-schema layer

PM-AUTO-01 deliberately never scans risks/blockers prose for keywords to
decide anything — that's unreliable in both directions. This task pushes
that same principle one step further: `review_decision.json` never
*interprets* anything either. Every field is either:

- copied verbatim from an explicit `task_meta.json` field (`risk`,
  `next_task_id`, `status_override`), or
- derived from a fixed rule over other structured data (auto-stop flags,
  or a check's `status` field in `quality_checks.json`).

Nothing in `generate_decision_package.py` reads `risks`, `remaining_blockers`,
`evidence`, or `suggested_next_task` to make a decision — those fields are
carried into `review_summary.md` and `next_task_draft.md` for a human to
read, never parsed by the script itself.

## Status derivation (in order)

1. **`status_override`** in `task_meta.json`, if set — always wins over
   everything below. Use this only when the automatic derivation would be
   wrong for a reason the automation can't see.
2. **Any auto-stop flag present** (`task_meta.json`'s `flags` array
   non-empty) → `BLOCKED`. The pipeline halts here — quality checks never
   run, and neither does the freeform next-task generator.
3. **Any quality check `FAIL`** in this cycle's `quality_checks.json`
   (produced by `generate_review_package.py` in the same pipeline run) →
   `FAIL`. Skipped checks do not count as failures.
4. **Otherwise** → `PASS`.

"This cycle's `quality_checks.json`" means its `generated_at` timestamp is
not older than `latest_report.json`'s — a stale file left over from an
earlier, unrelated run is never trusted to decide this task's status. If no
fresh `quality_checks.json` exists at all (e.g. the pipeline halted on
`BLOCKED` before quality checks ran), status defaults to `PASS` only by
*absence of a failure signal*, and the `reason` field says so explicitly —
this is not the same thing as claiming the checks passed.

## `next_task` derivation

- **PASS** → `task_meta.json`'s `next_task_id` field verbatim, or `null` if
  that field wasn't set. Never guessed from the free-text
  `suggested_next_task`.
- **FAIL** → always the fixed pattern `REWORK-<task_id>`, regardless of what
  `next_task_id` said. A failed task's next step is fixing itself, not
  moving forward to whatever was originally planned next.
- **BLOCKED** → always `null`. No next task can be determined until the
  blocker is resolved.

## Full field reference

See [`schemas/review_decision.schema.json`](./schemas/review_decision.schema.json)
for the authoritative JSON Schema (draft-07), with a description on every
field. Summary:

| Field | Type | Meaning |
|---|---|---|
| `task_id` | string | Copied from `task_meta.json`. |
| `status` | `"PASS"` \| `"FAIL"` \| `"BLOCKED"` | See derivation above. |
| `risk` | `"LOW"` \| `"MEDIUM"` \| `"HIGH"` | Copied from `task_meta.json`'s `risk` field, defaults to `MEDIUM` if omitted. Informational only — does not currently gate the pipeline. |
| `blocked` | boolean | `true` iff `status == "BLOCKED"`. |
| `next_task` | string \| null | See derivation above. |
| `requires_human_approval` | boolean | Always `true`. Fixed per PM OS rule. |
| `generated_at` | ISO 8601 string | When this decision was generated. |
| `reason` | string | One-line explanation of the status derivation, for audit/traceability — a log line, not a structured field. |

## New `task_meta.json` fields (PM-AUTO-03)

Three optional fields were added to the `task_meta.json` schema (see
`automation/reports/task_meta.example.json` for the annotated version):

- **`risk`** (`"LOW"`/`"MEDIUM"`/`"HIGH"`, defaults to `"MEDIUM"`) — a
  human/Claude judgment call, never inferred.
- **`status_override`** (`"PASS"`/`"FAIL"`/`"BLOCKED"`/omitted) — forces
  `review_decision.json`'s status, bypassing the automatic derivation.
- **`next_task_id`** (short string label, e.g. `"PM-AUTO-04"`, or omitted) —
  used verbatim as `next_task` on `PASS`. Deliberately separate from the
  longer, free-text `suggested_next_task` field, which is still used only
  in `next_task_draft.md`'s Objective section for human reading.

## `next_task_draft.md` content by status

| Section | PASS | FAIL | BLOCKED |
|---|---|---|---|
| Title | `next_task_id` or "(unassigned)" | `REWORK: <task_id>` | `UNBLOCK: <task_id>` |
| Objective | `suggested_next_task` text | Fix the failing check(s) from `<task_id>` | Resolve the blocker(s) preventing `<task_id>` from completing |
| Scope | Not yet scoped (PM to define) | List of failed check names from `quality_checks.json` | `remaining_blockers` text, or the flag list |
| Deliverables | TBD | All items in Scope must pass; no unrelated changes | Whatever removes the blocker(s) |
| Validation requirements | TBD | Re-run the same failing check(s), confirm PASS | Re-run `<task_id>`'s original validation once unblocked |
| Stop conditions | The 8 standard Auto-Stop flags, always listed | (same) | (same) |

Every draft carries the same "DRAFT — not an approved Task ID, nothing
executes this automatically" banner used throughout this automation layer.

## Usage

```
python3 automation/run_pm_pipeline.py automation/reports/task_meta.json
# On BLOCKED: exit code 2, review_decision.json still generated.
# On FAIL:    exit code 3.
# On PASS:    exit code 0.
```

Or run the decision-package step alone (reads `reports/latest_report.json`
and, if present and fresh, `reports/quality_checks.json`):

```
python3 automation/generate_decision_package.py
```

## CI suitability / future GitHub Actions integration

`run_pm_pipeline.py`'s own exit code now mirrors `review_decision.json`'s
status (0 = PASS, 2 = BLOCKED, 3 = FAIL, 1 = invalid `task_meta.json`) so a
CI step can gate purely on exit code, with `review_decision.json` available
as a build artifact for anything needing the structured detail (`risk`,
`next_task`, `reason`). Nothing in this layer calls GitHub's API or writes
a workflow file — wiring an actual `.github/workflows/*.yml` step is
out of scope for this task (see PM-AUTO-04 in Limitations/Recommended next
task).

## Limitations

- `risk` does not currently gate anything (e.g. a `HIGH` risk `PASS` is not
  treated differently from a `LOW` risk `PASS`). It's captured for a human
  or a future CI policy to act on, not enforced here.
- The freshness check for `quality_checks.json` compares ISO timestamps as
  strings, which works because both are generated with the same
  `datetime.isoformat(timespec="seconds")` format and the same local
  timezone offset — it is not a general-purpose timestamp comparison.
- `next_task_id` is a plain string with no format validation (e.g. nothing
  enforces a `PM-XXX-NN` pattern). A malformed or missing ID just means
  `next_task` is `null` or whatever was typed — the human review step is
  expected to catch that, same as it catches everything else this
  automation doesn't validate.
- No actual GitHub Actions workflow file was created — see above.
